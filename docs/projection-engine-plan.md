# Chronicaria Projection Engine — Implementation Plan

A plan to add **player rating progression projections** and **team-overall / power-ranking
projections** to chronicaria.github.io, grounded in a faithful reading of the BasketballGM
(zengm) simulation engine.

> Status: design only — nothing implemented yet.
> Priorities (stated by owner): **accuracy, creativity, stability**, in that spirit.

---

## 0. Executive summary

The site is a static dashboard generated by one Python script
(`scripts/league_generator.py`, ~7,400 lines) that bakes a BBGM JSON export into pre-rendered
HTML. There is no runtime data fetching and no charting library — charts are hand-rolled SVG.

The proposal is to add a new pure-Python module (`scripts/projections.py`) that **re-implements
the engine's exact player-development math** and runs a **Monte Carlo simulation** to produce, for
every player and team, a distribution of future ratings/overalls. From those distributions we
render confidence-banded "fan charts" (in the same SVG style already in use) and project future
team overalls and power rankings from each team's contracted roster.

The key reason for Monte Carlo (rather than a closed-form curve) is that the engine's development
is **inherently stochastic** — there is genuine season-to-season randomness with a specific
correlation structure — so honest projections require simulating many futures and summarizing them
with percentiles.

## 1. Ground truth from the game code

All file references are in `/Users/andrewpark/Desktop/Code/zengm`.

### 1.1 The 15 subratings
`src/common/constants.basketball.ts` (RATINGS array): `hgt, stre, spd, jmp, endu, ins, dnk, ft,
fg, tp, oiq, diq, drb, pss, reb`. (The site already labels these in `RATING_LABELS` / groups them
Physical / Shooting / Skill.)

### 1.2 Player development model — EXACT
`src/worker/core/player/developSeason.basketball.ts`. One call advances a player one year of age.
The logic, which we will port verbatim:

1. **Height bump (young only):** if age ≤ 21, roll `Math.random()`; +1 hgt if >0.99 (and age≤20),
   another +1 if >0.999. Rare.
2. **Base change (per season, SHARED across all ratings):**
   `calcBaseChange(age, coachingLevel)`:
   - Deterministic age curve: age≤21 → +2; ≤25 → +1; ≤27 → 0; ≤29 → −1; ≤31 → −2; ≤34 → −3;
     ≤40 → −4; ≤43 → −5; else −6.
   - **Noise added to base:** age≤23 → `bound(realGauss(0,5), −4, 20)`; age≤25 →
     `bound(realGauss(0,5), −4, 10)`; else → `bound(realGauss(0,3), −2, 4)`.
   - Coaching: `val *= 1 + sign(val) * coachingEffect(level)`; `coachingEffect = 0.09 * effect`,
     where `effect = levelToEffect(level)`; **DEFAULT_LEVEL = 34 ⇒ effect ≈ 0 (neutral)**.
3. **Per-rating update (loop over the 14 non-hgt ratings):**
   `rating += bound( (baseChange + ageModifier(age)) * uniform(0.4, 1.4), changeLimits[0], changeLimits[1] )`
   then `limitRating` clamps to [0,100] (with the engine's special rounding).
   - The `* uniform(0.4,1.4)` multiplier is **independent per rating**.
   - **Per-rating ageModifier & changeLimits:**
     - `shootingFormula` (ins, ft, fg, tp): ageMod 0 (≤27), 0.5 (≤29), 1.5 (≤31), else 2; limits [−3,13].
       → shooting *reverses* the aging decline; shooters hold/grow late.
     - `iqFormula` (oiq, diq): ageMod 4 (≤21), 3 (≤23), 0 (≤27), 0.5 (≤29), 1.5 (≤31), else 2;
       limits [−3,9] if age≥24 else [−3, 7+5*(24−age)]. → IQ explodes for young players.
     - `spd`: ageMod 0 (≤27), −2 (≤30), −3 (≤35), −4 (≤40), else −8; limits [−12,2].
     - `jmp`: ageMod 0 (≤26), −3 (≤30), −4 (≤35), −5 (≤40), else −10; limits [−12,2].
     - `endu`: ageMod `uniform(0,9)` (≤23!), 0 (≤30), −2 (≤35), −4 (≤40), else −8; limits [−11,19].
     - `dnk`: ageMod 0 (≤27), else 0.5; limits [−3,13].
     - `stre`: ageMod 0; limits [−∞,∞].
     - `drb, pss, reb`: ageMod = shootingFormula's; limits [−2,5].

**Correlation structure (critical for honest CIs):** within one simulated season, *all* ratings
share the one `baseChange` draw (a "good/bad development year" lifts/sinks the whole player), while
each rating additionally gets its own `uniform(0.4,1.4)`. We must reproduce both layers — not just
add independent noise per rating, which would understate overall-rating variance.

### 1.3 Player OVR — EXACT
`src/worker/core/player/ovr.basketball.ts`. Weighted linear combo of the 15 ratings minus
per-rating baselines, +48.5 intercept, then a piecewise "fudge factor", then round & clamp [0,100]:

```
r = 0.159*(hgt-47.5) + 0.0777*(stre-50.2) + 0.123*(spd-50.8) + 0.051*(jmp-48.7)
  + 0.0632*(endu-39.9) + 0.0126*(ins-42.4) + 0.0286*(dnk-49.5) + 0.0202*(ft-47.0)
  + 0.0726*(tp-47.1) + 0.133*(oiq-46.8) + 0.159*(diq-46.7) + 0.059*(drb-54.8)
  + 0.062*(pss-51.3) + 0.01*(fg-47.0) + 0.01*(reb-51.4) + 48.5
fudge: r≥68→+8; 50≤r<68→ 4+(r-50)*(4/18); 42≤r<50→ −5+(r-42)*(9/8);
       31≤r<42→ −5−(42-r)*(5/11); else −10
ovr = clamp(round(r + fudge), 0, 100)
```

We **derive projected OVR from the projected subratings each season**, never project OVR directly.
This guarantees internal consistency and lets us validate against the stored `ovr` exactly.

### 1.4 Team OVR — EXACT
`src/worker/core/team/ovr.basketball.ts`. Sort roster by player OVR desc, pad to 10 with 0s,
exponential-weighted sum of the top 10 → predicted MOV → scale to 0–100:

```
predictedMOV = -k + Σ_{i=0..9} a * e^(b*i) * ovr_sorted[i]
regular season: a=0.3334, b=-0.1609, k=102.98
playoffs:       a=0.6388, b=-0.2245, k=157.43
teamOvr = round( predictedMOV*50/15 + 50 )   (playoffs: additionally −40 before rounding)
```
Weights (reg.): #1=1.00, #2=0.851, #3=0.725, #4=0.617, #5=0.525, #6=0.447, #7=0.381, #8=0.324,
#9=0.276, #10=0.235. It is an **absolute** MOV-anchored scale (50 ⇒ even team), *not* normalized to
the league. (It can also accept a single `rating` key to produce per-skill team strength — useful
for "team three-point rating" style breakdowns.)

### 1.5 Power rankings
`src/worker/views/powerRankings.ts`. Composite score, sorted desc:
```
score = (actualMOV * gp)/numGames          # season-to-date performance
      + (teamOvr*0.6 - 30)                  # talent estimate from roster
      + (-10 + 2*winsLastTen)               # recent-form momentum (last 10)
```
For pure *future* projections (no games played yet) the first and third terms vanish, so projected
power rank ≈ ordering by projected team OVR; we should say so explicitly in the UI rather than
implying we modeled momentum we can't see.

### 1.6 Fuzz vs. true ratings
BBGM stores **true** ratings plus a `fuzz` value; the displayed rating a GM sees is
`round(true + fuzz)` (scouting uncertainty). The export's historical ratings rows are true ratings.
**Decision:** project on true ratings (the engine's actual state machine) and label projections as
true-talent. Optionally show a thin "scouting fuzz" band derived from `fuzz` magnitude, but keep it
visually distinct from the development-uncertainty band so the two sources of uncertainty don't get
conflated.

## 2. Core modeling approach

### 2.1 Why Monte Carlo
Development is stochastic (Gaussian base-change noise + per-rating uniform multiplier + rare height
bumps + the `endu`/young-IQ wide bands). No closed form gives an honest interval. We simulate
N futures per player and summarize with percentiles. This also exactly matches how the engine itself
estimates potential (`monteCarloPot` runs 20 sims and takes the 75th percentile of peak OVR — see
`src/worker/core/player/develop.ts`), which gives us a built-in validation target.

### 2.2 Faithful Python port
Port `developSeason`, `calcBaseChange`, `limitRating`, the player `ovr`, and team `ovr` into
`scripts/projections.py` as pure functions. Mirror the constants verbatim with a comment citing the
zengm source path + the commit/date of the pulled repo, so future engine updates can be re-synced.
Implement `realGauss`/`uniform` against a **seeded** RNG (see 2.4). One unit test per ported
function asserts parity with hand-computed values from the TS source.

### 2.3 Age handling
Age in a given season = `season - born.year`. To project player P to season S we apply
`developSeason` once per year from (current age + 1) up to the target age, carrying the mutated
ratings forward within each simulation path. (We project on a *copy* per simulation.)

### 2.4 Deterministic, reproducible builds
This is a static, version-controlled site rebuilt by GitHub Actions; non-deterministic output would
churn git diffs and undermine stability. So seed the RNG **per (pid, horizon)** with a fixed master
seed, e.g. `seed = hash(master_seed, pid)`. Same input league JSON ⇒ byte-identical projections ⇒
clean diffs. Expose `master_seed` as a CLI flag for experimentation.

### 2.5 Derive OVR each step
Within each simulation, after advancing the 15 subratings for a season, recompute player OVR with
the ported formula. Team OVR is computed from the per-simulation set of player OVRs (see 4.2). Never
average OVRs across simulations and then refit — always compute the statistic inside each sim, then
take percentiles of the statistic.

### 2.6 Confidence intervals
For each (player, future season): collect the N simulated values of each subrating and of OVR; report
median (P50) and bands (e.g. P10–P90 and P25–P75). For "potential," reproduce the engine's own
definition (P75 of the running *peak* OVR through age 29) so our "Pot" matches what the game shows,
and also surface a more transparent P90-ceiling / P10-floor.

### 2.7 Coaching assumption
`calcBaseChange` depends on coaching level (team budget). Plan:
- **Player pages:** default to neutral (DEFAULT_LEVEL=34 ⇒ ≈0 effect) so a player's projection is
  team-agnostic and stable across trades. Note the assumption in the UI.
- **Team projections:** optionally use each team's actual coaching budget level (read from team
  budget in the export) to reflect strong/weak development orgs. Provide a build flag to toggle.
The coaching effect is small (≤~9%) so this is a second-order refinement, not a correctness issue.

### 2.8 Validation / back-testing (accuracy gate)
The export already contains multi-season ratings history per player (e.g. 2021→2029). Use it:
1. **Formula parity:** recompute stored `ovr` from stored subratings for every player-season; must
   match the engine's stored value (modulo fuzz) to ~±0 after fudge/round. Gate the build on this.
2. **Back-test development:** for each player with ≥3 seasons of history, "stand" at an early season,
   project forward, and score the realized later seasons against our bands (coverage: ~80% of
   realized values should fall inside the P10–P90 band; median bias near 0). Produce a one-page
   `projections_report.md` artifact each build summarizing coverage, bias, and outliers.
3. **Pot parity:** our P75-peak should track the stored `pot` for under-29 players.
Document results; if coverage is badly off, the port has a bug — fix before shipping visuals.

## 3. Feature A — Player rating projections

**What the user sees on each player page (new section, below existing Development chart):**

1. **OVR fan chart.** Extend the existing `ratings_progress_svg` style: solid line = historical
   OVR; from the current season forward, a shaded band (P10–P90) with a median line, and the
   engine-style potential marker. Reuse the existing SVG grid/axis helpers so it matches the site.
2. **15-subrating small-multiples grid.** One mini fan chart per subrating (5×3 grid following the
   existing Physical/Shooting/Skill grouping), each showing history + projected median + band. This
   directly delivers the requested "projected progression of all fifteen subratings."
3. **Projection table.** Year-by-year future rows mirroring the existing `ratings_table`, but each
   cell shows `median (P10–P90)` for OVR and each subrating; visually distinguished (italic/greyed)
   from historical rows.
4. **Narrative tags (creativity):** auto-generated labels from the distribution — e.g. "Ascending"
   (steep positive median slope, young), "Late-career shooter growth" (tp/fg rising while spd/jmp
   fall), "High variance" (wide bands), "Cliff risk" (age ≥ 30 with steep spd/jmp decline). Cheap to
   compute from the sim output and adds editorial flavor.

Scope notes: project the player to the lesser of (a) some horizon (e.g. 6 seasons) and (b) a soft
age cap (e.g. until age ~40 / decline floor). Skip retired players. Handle players with thin history
gracefully (project from current ratings even with <2 historical rows).

## 4. Feature B — Team overall & power-ranking projections

This has two hard sub-problems: (1) *who is on the roster* in each future season, and (2)
propagating player uncertainty into a team-level distribution.

### 4.1 Future roster construction (the real difficulty)
Player projections are easy; knowing the *roster* in 2032 is not. Available signals in the export:
`contract.exp` (contract end year), `draftPicks`, free-agency status. Proposed layered approach,
each year of the horizon:
- **Contracted core:** players whose `contract.exp ≥ season` stay (project their ratings).
- **Expiring players:** model with an explicit, labeled assumption. Recommended default: a
  **re-sign probability** heuristic (e.g. keep key players, let end-of-bench walk) OR the simpler,
  more defensible **"contracts-only" mode** that just shows the team's *guaranteed* core declining
  and flags roster holes. Make the assumption a visible toggle/caption, never silent.
- **Incoming draft picks:** optionally seed rookies at replacement-to-prospect level using draft
  slot → expected rating priors; or exclude and label "current contracts only." Default: exclude
  from the headline number, mention as upside.
- **Roster holes:** if fewer than ~10 projected players, the team-OVR formula already pads with 0s,
  which realistically punishes thin future rosters — keep that behavior (it's honest) and annotate.

**Confirmed approach — both views, side by side, with a toggle.** Compute and cache *both*:
- **"Guaranteed core"** — contracts-only; unimpeachable baseline; roster holes left as 0-pads.
- **"Projected roster"** — adds re-sign probabilities for expiring players + draft-pick priors.
The team page (and projected-power-ranking board) defaults to "Guaranteed core" and lets the user
flip to "Projected roster" via the interactive toggle (§6). Each mode carries a one-line caption
stating its assumptions. Because both are precomputed into the embedded JSON, the toggle is instant
and needs no rebuild. The re-sign heuristic and draft-slot→rating priors live in clearly-isolated,
unit-tested functions so the speculative logic is easy to audit and tune independently.

### 4.2 Team-OVR distribution
Run **coupled simulations**: for sim iteration *k*, take each roster player's *k-th* simulated
rating set for that season, compute each player's OVR, then apply the team-OVR formula (top-10
sorted, exp weights, MOV scaling) → one team-OVR sample. Repeat over k=1..N → team-OVR distribution
per future season. (Coupling within a sim index is the correct way to capture that a team's outcomes
are the joint result of its players' development, not independent per-player medians summed.)

Deliverables on each **team page**:
- **Team-OVR trajectory fan chart** (history if available + projected median/band per season).
- **Contention window** readout: seasons where projected median team-OVR ≥ some contender threshold,
  with the band; plus a "core expiry timeline" bar showing when key contracts end (creativity:
  makes the championship window legible at a glance).
- **Per-skill team strength projection** (optional): reuse the team-OVR formula's `rating` mode to
  project, say, team 3-point or rim-protection strength forward.

### 4.3 Projected standings / power rankings (league page)
For each future season, order teams by projected median team-OVR to produce a **projected power
ranking**, with each team's band shown so ties/overlaps are visible. Be explicit that this is a
talent projection (the momentum/record terms of the real power-ranking formula are unknowable for
unplayed seasons — see 1.5). Optionally convert team-OVR→expected MOV→a rough projected win total
using the engine's MOV scaling, clearly labeled as an estimate.

## 5. Architecture & code plan

```
  projections.py           # NEW — pure engine port + Monte Carlo + aggregation
  projections_report.md    # NEW build artifact (validation summary)

  test_projections.py      # NEW — formula parity + backtest coverage
```

`projections.py` public surface (sketch):
- `develop_season(ratings, age, coaching_level, rng)` — verbatim port.
- `player_ovr(ratings)`, `team_ovr(player_ovrs, playoffs=False, rating=None)` — verbatim ports.
- `simulate_player(player, seasons_ahead, n_sims, coaching_level, master_seed)` →
  `{season: {ovr: {p10,p25,p50,p75,p90}, subratings:{key:{...}}, peak_pot}}`.
- `simulate_team(team, roster, mode, ...)` → per-season team-OVR distribution.
- `build_projection_cache(data, ...)` → one dict keyed by pid/tid, computed once per build and
  threaded into the existing render functions (so we simulate each player exactly once).

**Integration points in `league_generator.py`:**
- Compute the projection cache once in `generate_site()` after players/teams are parsed.
- `render_player_page()` (line ~2411): add `player_projection_section(...)` after
  `ratings_progress_svg(...)`.
- `render_team_page()` (line ~1324): add `team_projection_section(...)`.
- League/index or a new `projections.html`: projected power rankings.
- New SVG helpers mirroring `ratings_progress_svg` for band/fan rendering; new CSS classes in
  `assets/styles.css` for bands (reuse existing `chart-grid`/`chart-tick`/`line-*` vocabulary).
- **Embed per-entity simulation summaries as JSON** in each page and add a small chart JS module
  in `assets/` (see §6). Data is still baked at build time (no runtime fetch) — only rendering is
  client-side. Build a static median-line SVG fallback so pages degrade gracefully without JS.
- Both roster modes (§4.1) are precomputed into the embedded JSON so the toggle is instant.

### 5.1 Performance & stability
Worst case ≈ 900 players × N sims × ~6 seasons × 15 ratings. At N=1000 that's ~80M rating updates —
borderline slow in pure Python (could be minutes in CI). Mitigations, in order of preference:
- **Vectorize with NumPy:** simulate all N paths for a player as array ops (the math is simple
  arithmetic + clamps + a couple of RNG draws). This is the big win; likely <1s/player.
- **Tune N:** N≈500–1000 is plenty for P10/P50/P90; expose as a flag. Use N=200 for fast local
  iteration, full N in CI.
- **Cache:** simulate each player once; team/league features read the cached per-sim arrays.
- Guard against engine edge cases: `limitRating` rounding, [0,100] clamps, `stre` unbounded limits,
  the `endu`/young-IQ wide bands, height bumps. Unit-test these specifically.
- Determinism (seeded RNG) keeps rebuilds diff-clean and reproducible — directly serves "stability."

If NumPy is undesirable as a dependency, the Action already runs Python; adding NumPy is low-risk,
but a pure-stdlib fallback (smaller N) is acceptable for v1.

## 6. Visualization & UX — interactive (confirmed)

v1 is **interactive**. The generator embeds each entity's simulation summary as a small JSON blob
in the page; a lightweight JS module renders charts and reacts to user controls. Data stays
baked-in (no runtime fetch), preserving the offline/static-hosting model — only the *rendering* is
client-side.

**Charting approach (the one open item):** prefer a **thin custom SVG/Canvas module (~few hundred
lines)** over a heavyweight library — it keeps the dependency footprint near-zero, matches the
existing `chart-grid`/`chart-tick`/`line-*` CSS vocabulary and dark/light theming, and the chart
types here are simple (line + shaded band + hover). A small library (e.g. uPlot, ~40KB, very fast)
is an acceptable alternative if we want polish faster; avoid large bundles (Plotly/Chart.js) given
the site's load-speed ethos. Decide at Phase 1.

Interactive elements:
- **Fan chart:** historical solid line → projected median line → P10–P90 band (light fill) + inner
  P25–P75 band (darker). **Hover** reveals exact median + band values per season; **legend toggles**
  show/hide the bands or overlay potential.
- **15-subrating small-multiples:** grouped Physical/Shooting/Skill; hover-synced across the grid so
  hovering a season highlights it in all 15.
- **Player compare overlay:** reuse the site's existing compare concept to overlay two players'
  projected OVR fans (nice-to-have, Phase 5).
- **Team page:** team-OVR trajectory fan + contention-window bar + **roster-mode toggle**
  ("Guaranteed core" ⇄ "Projected roster", §4.1) that re-renders instantly from the embedded JSON.
- **Projected power-ranking board:** bands shown so overlap/uncertainty is visible; respects the
  roster-mode toggle.
- Graceful no-JS fallback: render a static `<svg>` median line at build time so pages remain
  readable if JS fails (progressive enhancement).

## 7. Risk register (accuracy & stability)

| Risk | Mitigation |
|---|---|
| Port drifts from engine math | Cite source paths + commit; unit tests assert parity; re-sync checklist when zengm updates |
| Independent-noise mistake understates OVR variance | Reproduce shared per-season `baseChange` + per-rating uniform exactly; backtest coverage check |
| Over-claiming future rosters | Default "guaranteed core / contracts-only" view; label all assumptions; never silent fill |
| Non-deterministic builds churn git | Per-pid seeded RNG; fixed master seed |
| Slow CI builds | NumPy vectorization; tunable N; cache one sim per player |
| Fuzz vs true confusion | Project true talent; keep scouting band visually separate |
| Power-ranking momentum unknowable for future | Project talent only; explicit caption |
| Real-player determinism blending (if league uses real players) | Check `gameAttributes` for `realPlayerDeterminism`; if active, account for srID blending or note exclusion |

## 8. Phased rollout

1. **Phase 0 — Engine port + validation (no UI).** `projections.py` + tests + `projections_report.md`.
   Gate: formula parity exact; backtest P10–P90 coverage ≈ 80%. *This is the make-or-break phase.*
2. **Phase 1 — Player OVR fan chart.** Single chart on player pages.
3. **Phase 2 — 15-subrating small multiples + projection table + narrative tags.**
4. **Phase 3 — Team-OVR trajectory + contention window + roster-mode toggle (both views).**
5. **Phase 4 — Projected power rankings / standings (respects roster-mode toggle).**
6. **Phase 5 — Polish:** player-compare projection overlay, per-skill team strength, editorial blurbs.

Each phase is independently shippable and leaves the site stable.
